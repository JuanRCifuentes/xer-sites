# クリティカル パス

クリティカル パスは、スケジュール内の依存アクティビティの最長シーケンスです。これにより、プロジェクトの最短期間が決定され、プロジェクトの終了日が直接定義されます。

実際的には、クリティカル パスは、最終期限に影響を与えずに遅延できない一連のタスクです。クリティカル パスのアクティビティに遅れが生じ、他に何も変更がなければ、プロジェクトの完了日も遅れます。

そのため、クリティカル パスは、Primavera P6 スケジュールの最も重要な出力の 1 つとなります。それは単なるフィルター、色、レポートではありません。スケジュールの運転完了とは何かについての説明です。

## クリティカル パスの意味

スケジュールには多くのアクティビティが含まれていますが、すべてのアクティビティが終了日に同じ影響を与えるわけではありません。一部のアクティビティにはフロートがあります。次のアクティビティやプロジェクトの終了に影響を与える前に、少し移動することができます。重要なアクティビティにはその柔軟性がないか、スケジュール方法や設定によっては柔軟性が最も低くなります。

クリティカル パスは、現在のロジック、期間、カレンダー、制約、ステータスに基づいてプロジェクトを完了するために必要な最小時間を示します。

```mermaid
flowchart LR
    A["プロジェクト開始"] --> B["デザインリリース"]
    B --> C["リードの長い機器を調達する"]
    C --> D["機器の設置"]
    D --> E["コミッション制"]
    E --> F["プロジェクトの完了"]
```

これが制御チェーンである場合、調達の遅れにより設置が遅れる可能性があります。設置が遅れると、試運転が遅れる可能性があります。試運転が遅れるとプロジェクトの完了が遅れる可能性があります。クリティカル パスは、チームがそのつながりを確認するのに役立ちます。

## それは遅らせることのできない連鎖です

クリティカル パスは、単に重要だと感じる作業ではありません。終了日を定義するのは、依存する作業順序です。

この区別が重要です。フロートがある場合、高価値アクティビティは重要ではない可能性があります。別のパスが完了を促進している場合、目に見えるクライアント マイルストーンは重要ではない可能性があります。小規模な技術的なアクティビティが、最終的なハンドオーバーにつながる唯一のチェーンに含まれる場合、重要になる可能性があります。

プロジェクト管理チームにとって、これによりクリティカル パスが意思決定ツールになります。それは次のような答えに役立ちます。

- 何がプロジェクト完了の原動力となっているのでしょうか?
- スケジュールに最も注意が必要なアクティビティはどれですか?
- 遅延が完了に直ちに影響を与えるのはどこでしょうか?
- 終了日を守ることができる回復アクションはどれですか?
- 報告されたパスは意味がありますか?

最後の質問は、スケジューラーが決して飛ばしてはいけない質問です。

## クリティカルフィルターを盲目的に受け入れないでください

Primavera P6 は重要なアクティビティを特定できますが、ソフトウェアはプロジェクトの意図を理解していません。提供されたデータ (ロジック、カレンダー、制約、期間、進行状況、スケジュール オプション) に基づいて計算されます。

データが弱い場合、クリティカル パスが奇妙に見える可能性があります。

アクティビティやマイ​​ルストーンは、実際にはプロジェクトを推進していなくても、クリティカル フィルターに表示される場合があります。これは、ロジックの欠落、ハード制約、古い日付、オープンエンド、異常なカレンダー、負のフロート、不正なステータス、または保持されたロジック設定が原因で発生する可能性があります。

スケジューラは専門的な判断を下さなければなりません。クリティカルパスに挑戦する必要があります。それは合理的だと思われるはずです。プロジェクト チームが認識するストーリーを伝える必要があります。

最終的な完了は実際の下流作業を伴わない管理上のマイルストーンによって行われるとパスに記載されている場合は、それに異議を唱えてください。パスが実際に実行を制御しないマイルストーンで始まっている場合は、それにチャレンジしてください。明確なインターフェイスがなく、パスが無関係な WBS 領域をまたいでいる場合は、それに挑戦してください。

クリティカル パスは、その背後にあるスケジュール モデルによって決まります。

## ベースライン スケジュールとクリティカル パス

最初のベースラインなど、一度も更新されていないスケジュールでは、クリティカル パスはプロジェクト開始マイルストーンで始まり、プロジェクト完了マイルストーンで終了することがよくあります。

それは一般的ですが、暗黙のルールではありません。

一部のプロジェクトには、重要な中間マイルストーンから始まるクリティカル パスがあります。たとえば、所有者がエリアを引き渡すか、許可が発行されるか、設計パッケージが承認ステータスに達するまで、建設を開始できない場合があります。その場合、ハンドオーバーまたは解放マイルストーンが制御パスの開始をトリガーする可能性があります。

同じ考え方がプロジェクトの終わり近くにも当てはまります。クリティカル パスは最終的な完了時に終了する可能性がありますが、中間の契約上のマイルストーン、引き継ぎ段階、システムのターンオーバー、または現在より制限されているクライアント アクセス日を推進する可能性もあります。

重要なのは、その道が最も伝統的な場所で始まり、終わるかどうかではありません。重要なのは、そのパスが論理的で、完全で、防御可能であるかどうかです。

## 進行中のスケジュール

スケジュールが進行すると、クリティカル パスの形状が変わります。完了した作業は、今後の完了を促進するものではありません。パスは現在のステータスの境界から始まる必要があります。

更新されたスケジュールでは、クリティカル パスは多くの場合、現在進行中のアクティビティ、開始準備の整った未開始のアクティビティ、または将来の作業へのアクセスを制御する有効なマイルストーンから始まります。また、そのイベントが真に次の重要な作業を推進している場合には、プロジェクト インターフェイスや引き継ぎマイルストーンから始まることもあります。

ここでデータの日付が重要になります。データ日付により、実際のパフォーマンスと予測作業が区別されます。データ日付の後のクリティカル パスは、残りの作業が完了に至るまでの過程を説明する必要があります。

パスが駆動ロジックのないアクティビティ、説明のないデータ日付の開始、または疑わしいマイルストーンで始まる場合、レビュー担当者は調査する必要があります。スケジュールには計算された経路が示されているかもしれませんが、信頼できるものではありません。

## マイルストーンに注意する

マイルストーンは、続行の通知、エリアの引き継ぎ、設計の承認、機械的な完了、システムの引き継ぎ、実質的な完了、最終的な完了などの重要なポイントをマークするため便利です。

しかし、マイルストーンはクリティカル パスのレビューを誤解させる可能性もあります。

マイルストーンには制約があるため、重要に見える場合があります。期間がなく、日付の境界にあるため、重要であるように見える場合があります。周囲のロジックが欠けているため、重要に見えるかもしれません。これは、マイルストーンが実際に制御実行チェーンの一部であることを自動的に意味するわけではありません。

クリティカル パスがマイルストーンから始まる場合は特に注意してください。聞く：

- このマイルストーンは実際の制御イベントを表しているのでしょうか?
- どのようなアクティビティや外部条件がマイルストーンを推進するのでしょうか?
- 節目までにどんな作品がリリースされるのか？
- マイルストーンはロジック主導ではなく制約されていますか?
- マイルストーン ロジックが修正された場合でも、パスは引き続きクリティカルになりますか?

マイルストーンが作業を制御しない場合、クリティカル パスのストーリーを定義することは許可されるべきではありません。

## ロジックを保持すればストーリーが変わる可能性がある

保持ロジックは、シーケンス外の進行を処理するために使用される Primavera P6 設定です。それは適切な場合もありますが、レビュー担当者が理解する必要がある点でクリティカル パスに影響を与える可能性もあります。

保持されたロジックが使用される場合、P6 は、後続の作業が順番どおりに開始されていない場合でも、先行ロジックを保持することがあります。これにより、計算されたクリティカル パスが変更される形で残りの作業が保留または順序付けされる可能性があります。

問題は、保持されたロジックが常に間違っているということではありません。問題は、スケジューラが現実的な予測を生成しているかどうかを理解する必要があることです。

ロジックが保持されているため、作業の実行方法が反映されなくなった関係を介してクリティカル パスが実行される場合、チームはステータス、ロジック、およびスケジュールのオプションを確認する必要があります。このパスは、単なる機械的な計算ではなく、防御可能な残りの計画を反映する必要があります。

## クリティカル パスを確認する方法

優れたクリティカル パス レビューでは、P6 の出力とスケジュールの判断を組み合わせる必要があります。

まず、最長パスまたはクリティカル パスのレポートを生成します。次に、アクティビティごとにパス アクティビティを確認します。先行者、後続者、関係タイプ、ラグ、制約、カレンダー、実際の日付、残りの期間、および合計フロートを確認します。

パスが意味があるかどうかを尋ねます。

- パスは信頼できる実行シーケンスに従っていますか?
- 有効な現在のドライバーから開始されますか?
- 正しい完了または制御マイルストーンで終了しますか?
- 制約によってパスが強制されていますか?
- 失われた関係が本当の原因を隠しているのでしょうか?
- 保持されたロジックがパスに誤解を招くような影響を与えていませんか?
- プロジェクトチームはこれを管理作業として認識していますか?

答えが「いいえ」の場合、クリティカル パスを自信を持って使用できるようにするには、スケジュールを見直す必要があります。

## 結論

クリティカル パスは、プロジェクトの終了日を定義する一連の依存タスクです。プロジェクトを完了するために必要な最小時間を示し、期限に影響を与えずに遅れてはいけない作業を特定します。

しかし、クリティカル パスは盲目的に受け入れられるものではありません。 P6 は、データが計算するように指示した内容を計算します。スケジューラは、結果が合理的、論理的であり、実際の実行計画と一致しているかどうかを検討する必要があります。

強力なスケジュールでは、クリティカル パスが明確なストーリーを伝えます。有効な現在のドライバーから開始し、実際の依存関係に従い、誤解を招く制約を回避し、進行状況を正しく処理し、正しい完了マイルストーンに導きます。

このストーリーが理にかなっている場合、クリティカル パスはプロジェクト管理において最も強力なツールの 1 つになります。そうでない場合は、予測を信頼する前にスケジュールをさらに検討する必要があるという警告です。
