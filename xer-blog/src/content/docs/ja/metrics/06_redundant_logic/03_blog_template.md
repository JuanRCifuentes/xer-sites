# Primavera P6 スケジュールの冗長ロジック

## タイトル

Primavera P6 スケジュールの冗長ロジック

## 推定リーディング時間 / スピーキング時間

5～10分

## ターゲットの長さ

750～1,500ワード

## 観客

このブログは、Primavera P6 スケジュール ロジックを評価するスケジューラー、プランニング エンジニア、プロジェクト管理エンジニア、プロジェクト マネージャー、および PMO レビュー担当者を対象としています。

## オープニングフック

ロジックが多いほど、必ずしもロジックが優れているとは限りません。スケジュールは、実際の制御を追加しない重複関係、繰り返される先行パス、および依存関係を保持していても、適切に接続されているように見えることがあります。

## 導入

ロジックは CPM スケジュールのバックボーンです。これは、作業が 1 つのアクティビティから次のアクティビティにどのように流れるかを示し、Primavera P6 が日付、フロート、クリティカル パスまたは最長パスを計算できるようにします。

冗長なロジックは、ネットワーク内の別の場所ですでに表されている依存関係を関係が繰り返す場合に発生します。これは、完全な複製、同じ 2 つのアクティビティ間の 2 番目の関係、または上流パスを繰り返す直接リンクである可能性があります。

このメトリクスは、明確に正当化されない限り、レビューして削除する必要がある冗長なロジック パターンを特定します。目標は未解決関係ゼロです。

## このパラメータの意味

このパラメータは、意味のある順序付けを追加しない関係がスケジュールに含まれているかどうかをチェックします。一般的な例には、FS と SS または FS と FF など、同じ先行者が同じ後続者に複数回接続されることが含まれます。

このメトリクスは、継承された先行ロジックも検索します。たとえば、アクティビティ A がアクティビティ B を駆動し、アクティビティ B がアクティビティ C を駆動する場合、別の実際の依存関係を表さない限り、アクティビティ A からアクティビティ C への直接の関係は不要になる可能性があります。

同じ 2 つのアクティビティ間の SS と FF は、重複が意図的に行われている場合には許容される場合があります。 SS 関係は後続処理の開始時期を制御でき、FF 関係は後続処理の終了時期を制御します。重要なのは、両方の関係が実際の状況を表しているかどうかです。

## この主題が重要な理由

ロジックが冗長であると、スケジュールが理解しにくくなります。これによりネットワークにノイズが加わり、どの関係が実際に日付を制御しているのかを確認することが困難になる可能性があります。

また、フロートを歪め、誤った走行経路を作成し、遅延解析をより困難にする可能性があります。 PMO またはスケジュールの品質レビュー中に、冗長ロジックにより、ネットワークが意図的に構築されたのか、それともコピーされ蓄積されたリンクによって組み立てられたのかという疑問が生じます。

## 悪い結果の一般的な原因

- クリーンアップされなかったコピーされたスケジュールセクション
- 同じ 2 つのアクティビティ間に複数の関係タイプが追加されました
- 日付を強制するために使用される FS と SS、または FS と FF
- 依存関係がチェーンを通じてすでに存在している場合でも、直接リンクが追加されました
- 既存のロジックをチェックせずに更新中に追加された関係
- スケジュールをより関連性のあるものに見せるために使用される不必要な依存関係

## 結果を改善する方法

### 1. 重複する関係パターンを見つける

まず、複数の関係によって接続されているアクティビティを特定します。 FS+SS、FS+FFの組み合わせには十分ご注意ください。多くの場合、一方の関係が実際の作業を実行し、もう一方の関係は冗長です。

SS と FF の組み合わせをより慎重に検討してください。これらは、重複する作業に開始コントロールと終了コントロールの両方が必要な場合に有効です。

### 2. 継承された先行ロジックを確認する

自身の先行者と同じ先行者および関係タイプを持つアクティビティを探します。同じ依存関係がパスを通じてすでに存在する場合、直接の関係は必要ない可能性があります。

このレビューは、ネットワークを通じて数ステップ遡って拡張することもできます。疑問は単純です。この直接的な関係は実際の依存関係を追加するのでしょうか、それともすでに存在するパスを繰り返すのでしょうか?

### 3. 不要な依存関係を削除する

アクセス、承認、引き継ぎ、建設順序、調達順序、リスク管理、または契約上の論理を表さない関係を削除します。

関係を削除した後、スケジュールを再計算し、フロート、駆動ロジック、最長パス、マイルストーンの日付を確認します。日付が予期せず変更された場合は、削除された関係が実際に有効であったかどうか、またはより明確な関係が必要かどうかを調査してください。

## シナリオ例

スケジュールには、FS 関係と SS 関係を持つアクティビティ B にリンクされたアクティビティ A があります。スケジューラは更新中に SS リンクを追加して、B をより早く開始するように強制しましたが、実際のハンドオーバーは FS リンクが引き続き制御します。

このレビューでは、SS 関係が実際の開始条件を表していないことが示されています。混乱が増すだけです。スケジューラは SS リンクを削除し、FS 関係を維持します。

別の領域では、アクティビティ A がアクティビティ B を駆動し、アクティビティ B がアクティビティ C を駆動します。また、アクティビティ A は、同じ関係タイプでアクティビティ C に直接リンクされています。チームは、個別のハンドオーバーやアクセス条件がないことを確認しています。 A-to-C の直接リンクは削除され、ネットワークは論理的に正しいままになります。

## 推奨される改善スケジュール

- 1 日目: メトリクスを実行し、結果を重複ペア、継承されたロジック、不要な依存関係ごとにグループ化します。
- 2 ～ 3 日目: まず、重要な関係およびほぼ重要な関係を確認します。
- 4 ～ 5 日目: 重複したロジックを削除し、スケジュールを再計算します。
- 6 日目: 例外を確認し、スケジュールの動きを確認します。
- 7 日目: 指標を再評価し、結果を文書化します。

## 避けるべき間違い

重複しているように見えるという理由だけでリレーションシップを削除することは避けてください。まずは実際の作業手順を確認してください。

重複したリンクは無害に見えるため、保持しないでください。冗長ロジックによってもフロート解析と駆動パス解析が歪む可能性があります。

SS と FF を自動的に間違ったものとして扱うことは避けてください。開始コントロールと終了コントロールの両方が必要な場合に有効です。

## 重要なポイント

- 冗長ロジックは、すでに他の場所で表されている依存関係を繰り返します。
- 同じアクティビティ間の FS と SS、または FS と FF は通常、レビューが必要です。
- SS と FF は、オーバーラップ開始コントロールと終了コントロールの両方が実際の場合に有効になります。
- 継承された先行ロジックにより、不要な直接リンクが作成される可能性があります。
- 目標は、未解決の冗長関係をゼロにすることです。

## 結論

冗長ロジックはスケジュールの品質を向上させません。これにより、ネットワークの読み取り、更新、防御が困難になります。

このメトリクスを確認することで、スケジューラは CPM ネットワークをクリーンかつ意図的に維持することができます。最適なスケジュール ロジックは、最も複雑なネットワークではありません。それは作品を正確に表現する最も明確なネットワークです。

## 行動喚起

次回の Primavera P6 スケジュール更新で冗長ロジックを確認してください。フラグが設定された関係ごとに、それが実際の依存関係を追加するのか、それともネットワークにすでに存在するロジックを繰り返すだけなのかを尋ねます。不要なものを削除し、意図的に残したものを文書化します。
