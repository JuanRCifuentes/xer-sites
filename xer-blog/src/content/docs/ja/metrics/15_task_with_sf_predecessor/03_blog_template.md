# Primavera P6 における SF の先駆者とのタスク アクティビティ

開始から終了までの関係は、CPM スケジューリングにおいて最も一般的ではない関係タイプの 1 つです。 Primavera P6 では、SF 関係は、先行アクティビティが開始されるまで後続アクティビティは終了できないことを意味します。まれなケースではこれが当てはまる場合もありますが、ほとんどのプロジェクト作業はこのように順序付けられません。

通常のタスク アクティビティの場合、開始から終了までの先行タスクはすぐにレビューの質問を提起する必要があります。つまり、この関係が表現しようとしている現実世界の状態は何ですか?答えが明確でない場合は、関係がスケジュールのロジックを弱めている可能性があります。

ほとんどのプロジェクトのスケジュールは、3 つの実際的な関係タイプに依存しています。終了から開始は、あるアクティビティが別のアクティビティを開始する前に終了する必要がある場合に使用されます。 Start-to-Start は、アクティビティを同時に開始できる場合、または 1 つの開始が別の開始に依存する場合に使用されます。 「終了から終了」は、1 つのアクティビティの完了が別のアクティビティの完了と結びついている場合に使用されます。これらの関係タイプは、通常、現場チーム、プロジェクト マネージャー、レビュー担当者にとって理解しやすいものです。

SFは違います。先行者の開始と後続の終了を結びます。つまり、前任者が開始するまで後続者の終了が保留されることになります。多くの建設、エンジニアリング、調達、試運転スケジュールでは、そのロジックを説明するのが困難です。別のタスクが開始されるまでタスクが終了できない場合、プランナーはそのルールの背後にある正確な動作条件を説明できる必要があります。

よくある問題は、ロジックのコピーです。スケジューラは、別のプロジェクトからアクティビティのグループをコピーしたり、外部ロジックをインポートしたり、グローバルな変更を適用したりすることがありますが、SF 関係は誰にも気づかれずにスケジュールに残ります。計算された日付は依然として許容できるように見えるため、関係は存続します。その後のレビュー中に、関係が実際の作業のやり方を反映していないため、論理パスを守るのが難しくなります。

もう一つの問題は日付管理です。アクティビティを希望の日付に終了させるために、SF ロジックがラグ付きで使用される場合があります。これにより、実際のドライバーが隠蔽される可能性があります。スケジュールに契約日、アクセス ウィンドウ、配送条件、または引き渡しマイルストーンが必要な場合、通常はその条件を直接モデル化する必要があります。スケジュールは、単に希望の終了日が得られるという理由だけで、紛らわしい関係タイプに依存すべきではありません。

「Start Permanent System Operation」からの SF 先行タスクを持つ「Temporary Bypass Operation」というタスクを考えてみましょう。この場合、常設システムが開始するまでバイパス操作は終了できません。代替システムが稼動するまでバイパスをアクティブにしておく必要がある場合、これは防御可能な SF 関係になる可能性があります。その場合でも、レビュー担当者はその関係に合理的に疑問を抱くため、スケジューラは理由を文書化する必要があります。

ここで、SF の先行タスクが「Start Cable Pulling」である「Install Cable Tray」という通常のタスクについて考えてみましょう。その関係を正当化するのはさらに困難です。ケーブルの引き込みを開始する前にケーブル トレイの取り付けを完了する必要がある場合は、ケーブル トレイからケーブルの引き込みまでの FS ロジックの方が適切である可能性があります。作業が重なる場合はSSやFFのロジックの方がわかりやすいかもしれません。 SF 関係は、実際の建設シーケンスを表さない限り、そのままにしておいてはなりません。

P6 での最良のレビュー方法は、アクティビティ ID、アクティビティ名、WBS、アクティビティ タイプ、先行 ID、先行名称、関係タイプ、ラグ、開始、終了、合計フロート、制約、クリティカル パスまたは最長パスのステータスを含むレイアウトを構築することです。 SF 先行タスクを含むタスク アクティビティをフィルターします。次に、最初に重要な調査結果とほぼ重要な調査結果を確認します。これらの関係は、報告されたプロジェクト推進要因に直接影響する可能性があるためです。

発見ごとに、簡単な質問をします。 SF関係モデル化とはどのような状態なのでしょうか？ FS、SS、または FF の方がロジックをより明確に説明できますか?日付を強制するためにラグが使用されていますか?その関係はクリティカル パスまたはマイルストーンのレポートに影響を及ぼしますか?それを保持する文書化された理由はありますか?

ターゲットしきい値は、タスク アクティビティ上の未解決の SF 先行関係がゼロである必要があります。これは、すべての SF 関係が自動的に間違っているという意味ではありません。それは、あらゆるSF関係は修正されるか、明確に正当化される必要があることを意味します。説明のつかない SF ロジックは、ロジックの監査と通信を困難にするため、ネットワークの信頼性を低下させる可能性があります。

関係が無効な場合は、実際のシーケンスと一致する関係タイプに置き換えます。別のアクティビティが終了した後にアクティビティを開始する必要がある場合は、FS を使用します。スタートがリンクしている場合はSSを使用します。仕上げを揃える必要がある場合は、FF を使用します。問題がマイルストーン、配信、承認、またはアクセス条件の欠落である場合は、その条件を表すアクティビティを追加または修正します。

修正後、スケジュールを再計算し、影響を受けるロジック パスを確認します。合計フロート、クリティカルまたは最長パス、マイルストーンの日付、および短期先取りレポートを確認します。目標は指標スコアを向上させることだけではありません。目標は、スケジュールを説明しやすくし、意思決定の信頼性を高めることです。

SF 先行者によるタスク アクティビティは小さいですが重要なシグナルです。多くの場合、コピーされたロジック、強制された日付、または不明確な順序が指摘されます。それらをレビューすることは、プロジェクト チームがそれらの弱点がレポートの問題になる前にロジック ネットワークをクリーンアップするのに役立ちます。
